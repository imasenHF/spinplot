# SpinPlot 架构与维护性优化规划

更新日期：2026-10-30（Asia/Shanghai）

状态：**规划已记录，尚未实施。** 本文件定义后续源码整理的目标、顺序和验收边界，不代表相关模块已经拆分，也不授权改变现有功能、科学数据语义或项目文件格式。

审查基线：正式 `main`，HEAD `5759d756d56daaefbbf9f8caab4c40bcd13ab964`；应用版本 **0.10.0**，项目格式 **11**，配置格式 **10**。后续执行前必须重新读取最新代码、分支、测试和工作流状态。

## 1. 优化目标

1. 降低应用入口和二维 UI 模块的职责密度，使局部功能修改尽量限制在对应模块。
2. 保持数据读取、物理处理、分析计算、绘图模型、渲染和界面交互之间的边界。
3. 建立统一的格式、静态检查、单元测试、浏览器回归和生产构建入口。
4. 使新增厂商文件格式、谱图分析方法、二维视图和导出格式具有明确的接入位置。
5. 在不改变科研数据含义和既有用户工作流的前提下逐步重构，避免大规模一次性改写。

优化原则：先建立回归基线，再提取模块；优先使用原生 JavaScript ES Modules 和现有 Canvas 绘图路线；不因依赖中存在 React 就迁移整个界面；不为尚未出现的需求预先建设复杂插件系统。

## 2. 当前代码基线与主要问题

### 2.1 已有基础

当前源码已经形成若干可独立维护的模块：

- `src/core/`：通用数值函数。
- `src/data/`：CSV 解析、曲线矩阵构造和二维数据结构。
- `src/processing/`：坐标、频率、信号处理与插值。
- `src/plotting/`：一维绘图、坐标缩放和子图空间计算。
- `src/twod/`：二维解析、模型、调色板、刻度、拟合、等值线、三维曲面和视图。
- `src/project/`、`src/export/`：项目兼容处理及多格式导出。
- `src/interface.js`、`src/styles/app.css`：部分界面组织与样式。

绘图场景已由 `src/export/scene.js` 组织，SVG、PDF 和栅格导出有独立模块；一维绘图也已从应用入口提取。现有数值测试、项目兼容测试和 Playwright 浏览器回归为继续整理提供了基础。

### 2.2 主要维护风险

**应用入口职责过多。** `src/main.js` 当前约 153 KB、560 行，包含应用状态、DOM 事件、文件导入协调、子图配置、绘图模型组装、项目配置恢复、历史记录、批量作图和绘图调度。文件存在较多超长行，静态统计最长行约 4,392 个字符。单行压缩会增加局部修改、审查和冲突处理成本。

**二维模块职责混合。** `src/twod/ui.js` 当前约 86.7 KB、1,875 行，包含二维数据模型、分析与拟合数据、控件生成、交互和 Canvas 渲染。该文件已经完成多行格式整理，当前主要问题是职责聚合，而非单行源码格式。

**模块依赖方向不够清晰。** `src/project/project.js` 为恢复二维数据而依赖 `src/twod/ui.js`；`src/plotting/oned.js` 也通过该模块调用二维渲染和布局函数。数据恢复、通用几何计算与 UI 模块之间仍有不必要的耦合。

**文件读取路径需要统一。** 常规导入和批量作图分别组织文件解析流程，CIQTEK、BES3T、CSV 等读取逻辑分布在应用入口和二维模块。增加格式时容易出现重复处理和行为差异。

**质量检查入口不统一。** `package.json` 目前只有 `dev`、`build`、`preview` 脚本，没有统一的 lint、format、test 命令。完整数值测试和浏览器基线对照主要位于 `modularization-preview.yml`，其触发范围为 `preview/modularization-*`；正式 Pages 工作流目前执行安装和生产构建，生产 HTTP 检查主要验证已部署页面版本及脚本资源。

**JavaScript 类型检查覆盖有限。** `tsconfig.json` 设置了 TypeScript strict，但未启用 `allowJs` / `checkJs`，不能据此认为主体 JavaScript 已经过严格类型检查。

### 2.3 本次审查的静态规模

| 文件 | 当前规模 | 主要职责或问题 |
| --- | ---: | --- |

## 3. 目标模块边界

目标数据处理路径：

```text
文件读取器
    │
    ▼
统一数据结构与元数据
    │
    ▼
物理坐标处理 / 信号处理
    │
    ▼
分析计算（峰、线宽、积分、投影、拟合）
    │
    ▼
绘图模型与布局
    │
    ▼
Canvas / SVG / PDF 渲染
    │
    ▼
屏幕显示或文件导出
```

界面与应用协调层负责接收用户操作、维护配置和调度上述模块，不在 DOM 事件处理器中实现科学计算。项目读写层负责文件格式校验、版本迁移和恢复，不依赖控件生成模块。

建议职责如下：

| 层 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| `app` | 应用初始化、状态协调、命令和事件绑定 | 谱线算法、文件格式细节 |
| `data` | CIQTEK、BES3T、CSV 等读取器，统一数据结构和元数据 | 绘图与界面控件 |
| `processing` | 坐标换算、频率校正、基线、幅度及插值 | DOM 操作 |
| `analysis` | 峰特征、投影统计、拟合和定量分析 | 直接修改原始数据或界面状态 |
| `plotting` / `rendering` | 绘图模型、布局、Canvas 与矢量场景 | 文件读取和科学数据预处理 |
| `ui` | 控件创建、参数展示、交互反馈 | 独立实现数值算法 |
| `project` | 项目/配置序列化、校验、迁移和恢复 | 依赖 UI 模块 |
| `export` | CSV、SVG、PDF、栅格格式序列化 | 重新计算与屏幕控件操作 |
| `workers` | 经性能测量确认需要异步执行的计算 | 未经测量而预先拆分全部计算 |

目录名称和最终文件粒度以实施时的实际依赖关系为准，不要求机械地为每个函数建立单独文件。

## 4. 分阶段实施路线

### 阶段 0：建立统一质量基线

**优先级：最高；不改变应用行为。**

- 增加 Prettier 与 ESLint 配置，明确 JavaScript、CSS、HTML 和测试代码的格式及静态检查规则。建议 JavaScript 格式宽度以 100 字符为基准；已有长文件分批整理，不把大规模格式变更与功能修改放在同一提交。
- 增加统一脚本入口，例如 `format:check`、`lint`、`test:unit`、`test:browser` 和 `check`。统一入口应保留现有二维、项目兼容、数值、导出和浏览器回归测试，不因脚本整理遗漏既有测试。
- 在 Pull Request 和正式 `main` 检查中运行相同的核心单元测试与生产构建；浏览器回归按执行成本分层，至少保留关键交互测试。正式部署不得仅依赖构建成功。
- 采用 JSDoc 和分批类型检查：先对 `core`、`data`、`processing`、`project`、`export` 试点 `allowJs` / `checkJs`，清理后再扩展到绘图、二维和应用入口。
- 检查未实际使用的依赖；React 依赖是否保留单独核实，不以此启动框架迁移。

**完成条件：** 本地存在单一质量检查命令；Pull Request 可自动运行核心检查；格式化与功能改动可分开审查；未降低现有测试覆盖范围。

### 阶段 1：收缩 `src/main.js`

**优先级：高；保持现有 DOM 和用户操作方式。**

按职责逐步提取，建议顺序：

1. 应用状态及初始化默认值。
2. 子图创建、删除、布局和子图状态操作。
3. 项目配置应用、撤销/重做和历史记录协调。
4. 文件导入与批量作图调度。
5. DOM 事件绑定和界面初始化。

可考虑在 `src/app/` 中建立 state、commands、subplots、events、bootstrap 等模块；具体命名根据现有函数调用关系确定。文件解析器放入 `src/data/readers/`，避免将解析细节继续留在应用入口。

`src/main.js` 最终作为组合入口，负责组装模块、注入依赖和启动应用。状态初期仍可使用普通 JavaScript 对象及显式操作函数，不引入额外状态管理框架。

**完成条件：** 文件导入、追加、清空、子图编辑、撤销/重做、项目恢复、批量作图和绘图调度均有对应回归；应用入口不再承载具体解析器和大段业务实现。

### 阶段 2：拆分 `src/twod/ui.js`

**优先级：高；保持二维数据和绘图结果一致。**

按以下职责提取：

- **二维模型与配置：** defaults、migrate、restore、orient、model 及数据结构校验。
- **二维分析：** overlap、scan correlation、投影统计、峰特征和拟合数据计算。
- **控件与交互：** 控件构建、输入校验、结果展示、拖拽与键盘事件。
- **二维渲染：** Canvas 绘制、投影、色标、等值线和三维曲面调用。
- **布局几何：** plotInsets、共享边距和主绘图区尺寸分配；通用部分应放在绘图层，不由 UI 模块导出。

拟合数值计算保留在纯函数模块；结果面板只读取拟合结果并负责显示。交互处理不得改变源矩阵。

优先解除 `src/project/project.js` 对 `twod/ui.js` 的依赖，使项目恢复只依赖纯数据模型；绘图模块通过明确的渲染与几何接口调用二维能力，不再依赖混合 UI 模块。

**完成条件：** 二维模型、分析、控件和渲染职责可以分别测试；项目读写不加载 UI；Heatmap、Stack、Overlap、Contour、3D、Variable scan、投影、色标和功率拟合行为保持一致。

### 阶段 3：统一数据读取与内部接口

**优先级：中高；为新仪器格式预留位置。**

- 将 CIQTEK、BES3T 和 CSV 解析器按格式放入独立 reader 模块。
- 普通导入与批量作图调用相同的解析入口，避免重复维护文件配对、元数据提取和错误处理。
- 明确一维曲线、二维矩阵、坐标轴、单位、频率来源和仪器元数据的内部接口。
- 解析器负责读取与校验；数据处理、分析和绘图模块消费标准化数据。
- 未识别的实验类型、单位缺失、文件配套不完整及坐标不一致继续明确报错，不静默猜测或降级。

**完成条件：** 同一文件经普通导入和批量流程得到一致的数据对象；各格式有正常样本、异常样本和元数据测试；原始数组和物理坐标语义保持不变。

### 阶段 4：按测量结果处理性能问题

**优先级：按需。**

- 建立代表性数据集的加载、矩阵分析、拟合和绘图耗时记录，覆盖常规数据与较大二维矩阵。
- 只有在主线程阻塞达到实际影响交互的程度时，才将适合的解析、矩阵分析或拟合计算迁入 Web Worker。
- Worker 使用明确的输入/输出结构，定义错误传递、任务取消和过期结果处理；DOM 与 Canvas 交互仍留在主线程。
- 评估 TypedArray、数据复制和转移的内存成本，不能只以单次计算耗时决定方案。

**完成条件：** 有优化前后基准数据；数值结果与主线程实现一致；取消、异常和连续提交任务均有测试。未达到性能需求时保留现有实现，不为使用 Worker 而增加复杂度。

## 5. 统一验收要求

每次模块提取或接口调整至少满足以下条件：

1. **科学数据语义：** 原始数组不被绘图和显示过程改写；一维处理结果 `y` 与显示偏移后的 `yd` 保持区分；二维矩阵仍为 Y 行、X 列；物理坐标、单位、频率来源和轴方向不被索引或像素坐标替代。
2. **处理算法：** 频率校正、磁场/`g` 换算、基线、幅度处理、投影统计、峰峰幅度、线宽和功率拟合均有明确输入、输出与适用条件。
3. **文件兼容：** 项目版本 9/10/11 和配置版本 10 的读取、保存、恢复及错误提示保持有效。除非单独提出格式迁移任务，不修改文件格式版本。
4. **数据格式：** CSV、CIQTEK、BES3T 的正常输入、异常输入、配套文件和元数据均有测试；私有实验样本不得提交公开仓库。
5. **绘图与导出：** 1D、2D、混排图、Canvas、SVG、PDF 和 CSV 输出保持一致；屏幕显示与导出使用同一绘图模型或明确的等价数据。
6. **浏览器交互：** 文件导入、坐标范围、投影、色标、缩放、双击、子图排序、撤销/重做和项目重载通过浏览器回归。
7. **构建与发布：** 单元测试、生产构建、浏览器回归、Pages 部署、生产 HTTP 检查分别记录。任何一项成功均不代表其余项目自动通过。
8. **科研验证：** 合成数据测试与真实仪器数据验证分开报告；涉及定量结论时记录数据集、采集条件、参数、预期值和允许误差。

## 6. 实施约束与暂不开展事项

- 每个阶段从最新正式 `main` 创建独立开发分支；一个 PR 尽量只处理一个职责边界。
- 大规模格式整理、模块迁移和功能行为变更分开提交，避免审查时无法区分纯重排与实际逻辑修改。
- 提取模块时优先保留原函数接口或提供兼容 re-export；确认调用点迁移后再删除旧入口。
- 不在同一任务中顺带修改无关 UI、科学算法或文件格式。
- 项目格式和配置格式变更必须单独说明迁移规则，并覆盖历史文件。
- React/其他框架迁移、后端服务、在线数据存储、插件机制及全面 Worker 化均不属于当前规划的前置任务；只有出现明确需求和测量结果后再评估。
- 正式合并、版本变更和发布按项目现有授权与验收规则执行。

## 7. 建议的首批实施顺序

1. **P0-1：** 为现有测试建立统一执行入口，核对所有测试均被纳入。
2. **P0-2：** 配置格式化与 lint 规则，先覆盖新代码和本轮修改文件。
3. **P0-3：** 将核心回归检查加入 Pull Request 与正式分支检查。
4. **P1-1：** 依据调用关系绘制 `src/main.js` 函数/状态依赖图，确定首批提取边界。
5. **P1-2：** 优先拆分文件解析和批量导入路径，再拆分子图操作与事件绑定。
6. **P1-3：** 将二维 restore/defaults 等纯模型函数从 `twod/ui.js` 分离，先解除项目模块对 UI 的依赖。
7. **P1-4：** 分离二维分析、控件和渲染；每次提取均执行对应数值和浏览器回归。

以上顺序是当前建议，具体执行范围以每项任务开始时重新检查的源码和用户最新要求为准。
